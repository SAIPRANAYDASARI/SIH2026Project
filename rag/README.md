# Manak Sahayak — hybrid multilingual RAG over the BIS corpus

Retrieval and grounded answering over the 254 BIS PDFs in `C:\bisnew`, with
three selectable search modes and a hard rule that nothing is answered unless
it can be traced to an indexed passage.

## Why this replaced the previous RAG

The earlier pipeline could not run on this machine and was answering from an
almost empty corpus:

| | Before | Now |
|---|---|---|
| Runtime | Postgres + pgvector + Redis + Celery + Ollama, all Docker-only | Plain Python — SQLite + a NumPy matrix |
| Docker / Ollama present | **Neither installed on this PC** | Not needed |
| Content indexed | 13 blobs, ~5.5 MB | 240 documents, 3,192 pages, 5,937 chunks |
| Hindi gazette text | Indexed as extracted, including corruption | Corruption detected and quarantined |
| Answer discipline | — | Refuses without a citation |

The retrieval *algorithm* was never the main problem. The corpus was empty and
the stack could not start.

## Install

```bash
python -m pip install pymupdf sentence-transformers torch numpy fastapi uvicorn pytest
```

`torch` is the CPU build; no GPU is required.

## Build the index

```bash
python -m rag.cli build     # extract, quality-gate, chunk, index  (~40 s)
python -m rag.cli embed     # dense vectors, BGE-M3 on CPU (slow, resumable)
python -m rag.cli stats     # coverage report
```

`build` is safe to re-run; `embed` only processes chunks with no vector yet, so
interrupting it loses nothing.

## Ask and search

```bash
python -m rag.cli ask "What are the grounds on which BIS can cancel a licence?"
python -m rag.cli ask "हॉलमार्किंग के लिए शुल्क कितना है?"
python -m rag.cli search "IS 17440" --mode keyword
python -m rag.cli compare "compulsory registration of electronics"
```

As a service:

```bash
python -m uvicorn rag.api:app --port 8100
```

`GET /health`, `GET /stats`, `POST /search`, `POST /ask`.

## Which LLM, and whose key

The only credential this system uses is `HOSTED_LLM_API_KEY` from your `.env`.
It is an **NVIDIA** key (`nvapi-...`); OpenAI keys begin with `sk-`. There is
no OpenAI account, key, or endpoint anywhere in this project, and nothing ever
contacts `openai.com`.

The default model is `openai/gpt-oss-20b`, which is confusing at first glance
and worth spelling out: `openai/` is a **publisher namespace inside NVIDIA's
catalog**, exactly like `meta/`, `mistralai/` and `nvidia/` in the same list.
`gpt-oss-20b` is OpenAI's Apache-2.0 **open-weight** model ("oss" = open source
software), and it runs on NVIDIA's servers, reached with your NVIDIA key.

Similarly, `HOSTED_LLM_PROVIDER=openai` in `.env` names a *wire protocol*
(the OpenAI chat/completions request format, which NVIDIA NIM implements),
not a vendor.

Only two models in NVIDIA's catalogue actually answer for this account —
the rest return `404 not found for account` or `503 overloaded`, including the
`nvidia/nemotron-3-ultra-550b-a55b` originally configured in `.env`. Verified
on a real grounded BIS prompt:

| Model | Result | Latency | Citations |
|---|---|---|---|
| `openai/gpt-oss-20b` | works | 18 s | correct, none invented |
| `nvidia/nemotron-3-super-120b-a12b` | works | 61 s | correct, none invented |

Both are in `FALLBACK_MODELS`, fastest first. Models that 404 are deliberately
**not** listed: an unavailable model still consumes one of the three attempts a
question is allowed, so a dead entry burns a real retry for nothing.

Because `gpt-oss-20b` is open-weight, it can be self-hosted later with no code
change — point `BIS_LLM_BASE_URL` at your own endpoint and set
`BIS_LLM_MODEL` accordingly.

## Cost — what can and cannot be billed

**Exactly one component of this system contacts a paid service:** the chat
completion that writes the final answer, sent to `integrate.api.nvidia.com`
using the key in your `.env`. There is a test (`test_budget.py`) that fails the
build if a second external URL is ever added to the package.

Everything else is free by construction, because it runs on your machine:
PDF extraction, the quality gate, indexing, **embeddings (local BGE-M3)**, and
**all three search modes**. Once built, the index needs no network at all.

Four guards stand in front of the one billable call:

| Guard | Setting | Default |
|---|---|---|
| Master switch — no code path can reach the network | `BIS_LLM_ENABLED=false` | on |
| Daily call cap, enforced locally *before* a request is sent | `BIS_LLM_DAILY_CALL_LIMIT` | 200 |
| Max requests generated by **one** question (retries + fallbacks combined) | `BIS_LLM_MAX_ATTEMPTS` | 3 |
| Max tokens per call | `BIS_LLM_MAX_TOKENS` | 1200 |

The attempt cap matters: without it, a provider outage turns a single question
into a storm of billable retries.

Check what has been spent at any time:

```bash
python -m rag.cli usage        # or GET /usage
```

The counter persists in `rag_index/llm_usage.json`, resets daily, and is
**fail-closed** — if it cannot be read, calls are refused rather than allowed
through unmetered.

### Guaranteed-zero-cost mode

```bash
python -m rag.cli ask "On what grounds can BIS cancel a licence?" --offline
```

Offline mode quotes the most relevant sentences **verbatim** from the retrieved
documents. No model writes anything, so it cannot fabricate and cannot cost
anything. It is also what the system falls back to automatically when the LLM
is disabled or the daily budget is spent — questions keep working, they just
stop being summarised.

To make the whole system permanently incapable of spending, set
`BIS_LLM_ENABLED=false` in `.env`. Retrieval and offline answering continue to
work unchanged.

> One thing this repo cannot tell you: NVIDIA's own billing terms for your
> account. The API returns no quota or credit headers, so the caps above are
> enforced locally rather than read from the provider. Confirm your plan's
> limits with NVIDIA directly.

## The three search modes

| Mode | Engine | Strong at | Weak at |
|---|---|---|---|
| `keyword` | SQLite FTS5 / BM25 | Exact IS numbers, gazette S.O. numbers, form and product names | Paraphrase; no cross-language matching |
| `semantic` | BGE-M3 vectors, exact cosine | Meaning, paraphrase, Hindi→English | Rare identifiers it has no strong representation for |
| `hybrid` | Reciprocal Rank Fusion of both + identifier boost | General use — **the default** | Slightly slower than either alone |

Fusion combines *ranks*, not scores: BM25 magnitudes and cosine similarities
are not on comparable scales, so mixing them directly would need a tuning
constant per corpus. RRF needs none.

## Multilingual behaviour

The corpus is bilingual, but its Hindi is frequently **not machine-readable** —
see the quality gate below. So multilingual support works cross-lingually
rather than by indexing unreliable Hindi:

1. A Hindi question is embedded with BGE-M3, which places Hindi and English in
   one shared vector space. Measured on this model: a Hindi query and its
   English equivalent score **0.859** cosine, against 0.454 for a different
   English topic.
2. It therefore retrieves the **clean English legal text** that actually
   answers it.
3. The answer is written in Hindi, with the operative English wording quoted
   verbatim so the user can check it against the original PDF.

The system never generates Hindi legal wording and presents it as the text of
an order.

## The quality gate — why some pages are excluded

Many BIS gazette PDFs extract without error but produce text no one can read:

| What is in the PDF | What extraction produces |
|---|---|
| Legacy Krutidev/ISCII font | `jftLVªh laö Mhö ,yö&33004@99` |
| Broken glyph→Unicode map | `केन्‍द रीय सरक र क` (spurious "सरक" spliced in) |
| No glyph mapping at all | `/uni0909/uni092A/uni092D` |
| Latin wedged into Devanagari | `हॉलमा[कग`, `असेZयग` |

Indexing that is worse than skipping it: it is unsearchable, and if it reached
an answer it would look like authoritative legal text while being gibberish.
So `rag/quality.py` scores every line and drops the ones that fail, recording
the reason. Current corpus outcome:

```
pages_ok       2630   (82%)  indexed
pages_corrupt   376   (12%)  rejected by the quality gate
pages_scanned   157   ( 5%)  image-only, no text layer — would need OCR
```

PyMuPDF is used rather than pypdf specifically because pypdf emitted 2,880
`/uni` escapes on a single hallmarking page where PyMuPDF emits none.

**This is a real coverage limit, and it is reported rather than hidden.**
`python -m rag.cli stats` lists exactly which documents lost pages. The
157 scanned pages are the main gap; OCR would be the way to close it.

## How fabrication is prevented

1. **Retrieval gate** — if nothing clears a relevance floor, the question is
   refused *before* an LLM is called. No context, no answer.
2. **Constrained prompt** — only the supplied passages may be used; every
   factual sentence needs an `[S#]` marker; IS numbers, dates, fees, penalties
   and validity periods must never be guessed.
3. **Post-generation validation** — citation markers are checked against the
   passages actually supplied. Invented ones are stripped and reported, and an
   answer with **no** valid citation is downgraded to a refusal, with the
   retrieved passages shown so the user can read the primary source.
4. **Honest provenance** — only the 13 files with a recorded download URL get a
   `source_url`; the rest get null rather than a plausible-looking guessed
   bis.gov.in link.

A refusal is a correct outcome here, not a failure.

## Tests

```bash
python -m pytest rag/tests -q
```

The quality-gate tests use real strings sampled from the corpus, not synthetic
examples. `test_answer.py` asserts the grounding guarantees above — including
that an uncited claim is never presented as an answer.

## Known limits

- **157 scanned pages are not indexed.** No OCR step exists yet.
- **12% of pages are excluded as corrupt.** Mostly Hindi halves of bilingual
  gazettes whose English half *is* indexed, so the legal content is usually
  still covered — but not always.
- **`_meta/qco_master.csv` is a skeleton.** Its enforcement dates and
  exemptions are mostly `NOT_EXTRACTED_manual_review_needed`; the corpus notes
  say so, and this pipeline does not treat those placeholders as facts.
- **Answer quality depends on a hosted LLM.** NVIDIA NIM returns 503/404
  unpredictably per model, so `rag/llm.py` falls back across several models.
  Retrieval itself is fully local and always works.
- **No reranker.** A cross-encoder rerank stage would likely improve
  precision@k further; RRF plus the identifier boost is what is in place today.
